==========================================================
  8K 鼠标回报率测试器 MousePoller8K  使用说明
  适用：Windows 10 / 11  64 位，单文件绿色版，免安装
  版本：v1.2（程序同 v1.1；本版补充各指标的详细解读）
==========================================================

【这是什么】
一个原生 Windows 小程序，用来测鼠标的 USB 回报率（轮询率 / Polling
Rate，单位 Hz），最高可准确测到 8000Hz（8K）。双击 MousePoller8K.exe
即可运行，不需要安装，不依赖任何额外运行库（只调用系统自带 DLL）。

【为什么网页最多只能测到 4K，而它能测到 8K】
网页测试器的瓶颈不在鼠标，而在浏览器：
  1) 浏览器会把高频的 mousemove / pointermove 事件“合并”
     （event coalescing），一帧里多次硬件上报只给你一个事件；
  2) 事件回调受浏览器主线程和显示器刷新率（通常 60~240Hz）节拍限制；
  3) JS 计时器 / 时间戳精度有限，且页面渲染会抢占输入处理。
所以 8000Hz 的鼠标在网页里往往被压到 1000~4000Hz，且数字乱跳、偏低。

本程序绕开浏览器，直接走操作系统底层：
  - Raw Input（原始输入，WM_INPUT）：鼠标每产生一次硬件上报，就收到
    一条消息，一报一消息，不做任何合并；
  - QueryPerformanceCounter 高精度计时，分辨率约 0.1 微秒，远高于
    8000Hz 所需的 125 微秒；
  - “采样”和“绘制”分离：收消息时只记一个时间戳（极快、不丢消息），
    界面每 30ms 才刷新一次，不会因为画图拖慢输入；
  - 进程提升到高优先级，减少系统调度造成的抖动。

【怎么用】
  1. 先在鼠标驱动里把回报率（Polling Rate / Report Rate）设到你想测
     的档位（如 8000Hz）；
  2. 双击打开 MousePoller8K.exe；
  3. 在窗口区域内“快速且尽量匀速”地来回移动鼠标 2~5 秒；
  4. 看左上角 CURRENT 的大数字就是当前回报率；按 R 键清零重测。
  注意：鼠标静止时很多鼠标会自动降频甚至停止上报，数字会掉到 0、
  显示 IDLE，这是正常现象，测回报率一定要在“持续移动”时读数。

【怎么判断是不是“真 8K”（重点）】
  - CURRENT / AVERAGE / 上方波形都是“滑动平均”：只要手移动得不够匀速、
    偶尔夹杂一次较长间隔，平均值就会被拉到 8000 以下。波形没有一直顶到
    8000，并不代表鼠标没在发 8K；
  - 真正可靠的判断看两处：
      ① MODE(typical)：把所有上报间隔取“最常见”的一档再换算成 Hz，
         不受手速忽快忽慢影响，直接反映鼠标的真实档位。稳定 8K 时
         这里应显示 ~8000Hz；
      ② 下方间隔分布柱状图：稳定 8K 时柱子应明显聚拢在 125us 的 8K
         参考线附近。只要这里有成规模的柱群（主峰扎在 125us），就说明
         鼠标确实在以 8K 上报、确实发出了 8K 数据包；
  - 开了 8K，为什么 AVERAGE / MODE 经常不到 8000（这很正常，别焦虑）：
    鼠标只在“真正移动”时才按 8K 密集上报，滑得慢、中途停顿或抬手都会
    混进更长的间隔，平均值立刻被拉低（慢滑时平均掉到四五千很常见）；
    只有快速、持续、尽量匀速地画圈时，MODE 才会贴近 6000~8000。只要
    柱状图 125us 处有成规模柱群，就证明它确实在发 8K；
  - “发得出 8K 信号”和“全程稳得住 8K”是两回事：前者看 MODE / 柱状
    主峰即可确认；后者要在持续匀速移动时看 CURRENT 能否长期贴近
    8000、JITTER（抖动）够不够小，并且还取决于 CPU、USB 口、游戏帧率、
    屏幕和手速。稳不住时降到 4K/2K 往往更顺滑，完全不必为数字焦虑。

【各指标含义（分三组，别被英文吓到）】
  第一组 · 你现在到底在多少回报率
  CURRENT       当前回报率（最近 512 次上报的滑动平均，最跟手、一直在动）
  AVERAGE       从按 R 清零到现在的平均回报率
  PEAK          整段里某一瞬间冲到的峰值，只代表“最快的一下”，不代表一直
                这么高；内置 110us 噪声门限，不会再出现几万 Hz 的假峰值
  MODE(typical) 众数档位：出现最多的间隔换算成 Hz，= 你大多数时候所在的
                档位，判断真实档位最可靠，优先看它

  第二组 · 间隔本身（单位都是微秒 us，稳定 8K ≈ 125us）
  AVG INTERVAL  相邻两次上报的平均间隔，和 AVERAGE 是一回事的两种写法
                （间隔越短，回报率越高）
  JITTER(std)   间隔标准差，衡量“整体匀不匀、抖不抖”：每次都≈125us 它
                就很小；忽大忽小它就大、画面也更容易周期性卡顿。越小越稳
  MIN GAP       整段里出现过的“最小那一个间隔”，是单次最快极值（和 PEAK
                对应）。★它和 JITTER 的区别：JITTER 看“整体稳不稳”
                （一大堆间隔的离散程度，是“面”），MIN GAP 看“最快的那
                一下”（单个极值，是“点”），别把两者当成一回事

  第三组 · 计数与图
  EVENTS        收到的“有效”硬件上报总数（被门限剔除的虚假重复不计）
  ELAPSED       测量时长（秒）。它越长、样本越多，上面的平均值越可信；
                刚测零点几秒时数字乱跳是正常的
  上方折线图    近期回报率随时间的波形（越平越稳）
  下方柱状图    上报间隔的分布。稳定 8K 时主峰应集中在 125us 附近
                （图中 8K 参考线处），越聚拢越好

【回报率与间隔对照表】
  125Hz -> 8000us     1000Hz -> 1000us
  250Hz -> 4000us     2000Hz ->  500us
  500Hz -> 2000us     4000Hz ->  250us
                      8000Hz ->  125us

【测到 8K 的前提】
  - 鼠标本体和其驱动/固件支持 8000Hz，并已在驱动中选中；
  - 无线鼠标请用原装高规格接收器并靠近，或直接用有线连接；
  - 尽量插主板后置 USB 口；测试时关闭特别吃 CPU 的程序；
  - 8000Hz 下 CPU 占用会比 1000Hz 高，这是正常现象。

【v1.1 修复了什么 / 备注】
  - 修复 PEAK 偶尔飙到 4~5 万 Hz 的问题：根因是系统（或脚本/软件）
    在极短时间内重复投递输入、旧版噪声门限又错误地以这些“假事件”为
    时间基准，导致下一次间隔被算得极短。新版把噪声门限设为 110 微秒
    （对应约 9kHz，真实 8K 为 125us，完全不受影响），且被判定为噪声
    的事件不再计入任何统计、也不会挪动时间基准，因此 PEAK 不会再
    出现物理上不可能的超高值；
  - 程序不联网、不写注册表、不保存任何文件，可随时直接删除。
